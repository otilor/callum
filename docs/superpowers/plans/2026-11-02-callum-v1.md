# Callum v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build Callum, a self-hosted outreach app that reaches people by email, LinkedIn and X within safe limits and hands the user only the people who reply, with the v2 "Daylight" screens.

**Architecture:** One Node 22 TypeScript process: Hono HTTP API + SSE, a scheduler loop, channel adapters, and SQLite via `node:sqlite`. The engine is pure functions over a `Clock`. A React + Vite SPA is served by the same process.

**Tech Stack:** Node 22 (ESM), TypeScript 5.9 (not 7), Hono 4 + @hono/node-server, node:sqlite, nodemailer, imapflow, mailparser, Playwright 1.63.0 (`playwright` package, matches the preinstalled browser), @anthropic-ai/sdk + zod 4, csv-parse, React 19, Vite, Vitest + @testing-library/react + jsdom, @fontsource/onest.

**Execution order:** Tasks 1–6, then **Task 21 (projects in the data layer)**, then Tasks 7–20, then **Task 22 (Electron desktop app)**.

**Spec:** `docs/superpowers/specs/2026-11-02-callum-v1-design.md` (binding, including §Projects), with `docs/design/v2-journey.md` (design doc), `docs/design/v3-screens.md` (the v3 screens brief) and `docs/design/boards/*.dc.html` (V2*, V3* and V4* boards; V4 = projects) (visual and copy reference; plain HTML/CSS with `{{holes}}`, `sc-for`/`sc-if` templating and a `class Component` logic block).

## Global Constraints

- Node `>=22.13`. ESM only (`"type": "module"`). Strict TypeScript (`strict: true`, `noUncheckedIndexedAccess: true`).
- All timestamps stored and passed as ISO 8601 UTC strings (`new Date().toISOString()`); time-zone math only in `src/server/engine/time.ts`.
- No module reads the wall clock directly: everything time-dependent takes a `Clock` (or a `Date`) argument.
- Test output must be pristine: no `ExperimentalWarning` from `node:sqlite`, no React act() warnings, no stray logs.
- Product numbers (verbatim from spec): sending hours 9:00–17:00 Mon–Fri recipient time; email cap 20 (days 0–6) / 70 (days 7–13) / 120 (day 14+); LinkedIn 15 invites/day, 7/day for 7 days at half pace, 40 messages/day; X 20 DMs/day; touch gaps 4 then 6 days, rest 4 days after touch 3, rest lasts 90 days; LinkedIn invite timeout 14 days, follow-up 5 days after thank-you, thank-you at next 11:00 recipient-local weekday; channel switch gap 7 days; 10 first hellos need an OK; Undo window 10 seconds; invite note max 280 characters.
- Opt-out line, verbatim, appended to every email body after a blank line: `If this isn't for you, just reply stop and I won't write again.`
- Copy rules (all UI and generated text): calm colleague, first names, plain words, **no exclamation marks**, exact times ("Thursday at 9:00", never "soon"). Say people / hello / follow-up / talking / resting / pause / Callum; never leads, prospects, contacts, touch, step, cadence, engaged, churned, disable, "the AI".
- Visual tokens: white ground; ink `#1D2140`; slate `#646B85`; mist `#F4F5F9`; line `#E7E9F0`; sun `#FFB020` (tint `#FFF3D6`) only for people who replied and Callum's voice; green `#22B07D`; error tint `#FFF1EC` with icon `#D9480F`; stage rings stranger `#D5D9E4`, hello `#A9B8F5`, following `#6E86F2`, talking `#3F52D9`; font Onest. Light mode only. No dashboards, charts, percentages or open rates. No ALL-CAPS labels.
- **It has to work** (Gabriel, verbatim: "it has to work. not just boilerplate code."): no stubs, no TODOs, no fake success paths, no `throw new Error('not implemented')`; every route, button and adapter does the real thing end to end. Demo adapters exist only for demo mode and tests, never as a fallback in real mode.
- Never send text containing a placeholder (`[ANY CAPS]`, `{{x}}`, `{x}`).
- Never message a person whose status is `stopped`, `closed`, `removed` or `held`, or anyone on the dock, automatically.
- Secrets (SMTP password, X tokens, LinkedIn cookie) live only in the `channel_secrets` table and are never returned by any API route.
- Commit after each task with a conventional-commit subject; end every commit message with:

## Review Focus

1. **Time zones and DST:** a recipient in `America/New_York` across the March DST change while the user is in `Africa/Lagos` must still get sends only 9:00–17:00 their time. Test pinned in Task 2.
2. **Double sends:** two overlapping `tick()` calls, or a tick racing an Undo, must never send one outbox item twice or send an undone one. Test pinned in Task 9.
3. **Handle matching:** inbound mail from `Kemi@OkoPay.com` or a LinkedIn URL with `www.`, a trailing slash or a query string must match the stored person; an unknown sender is ignored. Test pinned in Task 1.
4. **Stop beats schedule:** a "stop" reply that arrives in the same tick as a due follow-up must cancel it before it sends. Test pinned in Task 9.
5. **Messy lists:** a CSV with a BOM, `;` separators, blank rows, duplicate people, or no usable channel must import the good rows and report each skipped one with a reason. Test pinned in Task 8.

**Interfaces:**
- Consumes: Task 1 types; Task 2 `nextSendingTime`, `nextLocalHour`, `addLocalDays`, `addDays`.

  - `chooseChannel(p: Person, connected: Channel[]): Channel | null` — first of `email` (needs `email`), `linkedin` (needs `linkedinUrl`), `x` (needs `xHandle`) that is in `connected`.
  - `stageFor(touches: number): Stage` — 0 stranger, 1 hello, 2–3 following.
  - `nextKind(p: Person): OutKind | null` — email/x: touches 0 → `hello`, 1–2 → `follow_up`, 3 → null. linkedin: touches 0 → `invite`; `linkedinState === 'connected'` and touches 1 → `thanks`; touches 2 → `follow_up`; otherwise null (waiting for acceptance).
  - `afterSent(p: Person, kind: OutKind, sentAt: Date, tz: string): Partial<Person>` — for auto kinds: `touches + 1`, `stage = stageFor`, `lastTouchAt`, `nextTouchAt` per spec (`hello` → +4 local days; first `follow_up` → +6; last touch → null and `restUntil` not yet set; `invite` → `linkedinState 'invited'`, `invitedAt`, `nextTouchAt null`; `thanks` → +5 days). For user kinds (`reply`, `booking`, `close`): see `afterUserSent`.
  - `afterUserSent(p: Person, kind: 'reply' | 'booking' | 'close', at: Date): Partial<Person>` — reply → `status 'active'`, `stage 'talking'`, `badge 'sent'`, `draft null`, `nextTouchAt null`; booking → same with `badge 'booked'`; close → `status 'closed'`, `draft null`, `nextTouchAt null`.
  - `onAccepted(p: Person, at: Date, tz: string): Partial<Person>` — `linkedinState 'connected'`, `nextTouchAt = nextLocalHour(at, tz, 11)`.
  - `restDue(p: Person, now: Date): boolean` — active, touches 3, `lastTouchAt + 4 days <= now`; or linkedin invited and `invitedAt + 14 days <= now` with `linkedinState 'invited'`.
  - `rest(p: Person, now: Date): Partial<Person>` — `status 'resting'`, `restUntil = now + 90 days`, `nextTouchAt null`.
  - `wake(p: Person): Partial<Person>` — back to `active`, `stage 'stranger'`, `touches 0`, `linkedinState 'none'`, `restUntil null`, `nextTouchAt null`, `badge null`.
